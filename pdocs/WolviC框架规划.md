# WolviC 框架规划

> 状态：草案（2026-10-13，起草中；§1–§3 已完成，后续章节待定）。

## 1. WolviC 的功能定位和主要特性

WolviC 是面向高性能处理器、人工智能处理器等控制密集型大规模数字电路的建模、设计、验证一体化框架，以高性能仿真引擎为基座，在同一套 C++ 环境中实现从微结构探索到 RTL 交付的完整研发流程。

框架的三项核心能力如下：

- **建模**：建立周期精确的 CModel，实现微结构探索，后期用作验证的参照标准（golden reference）；
- **设计**：以可综合描述完成电路实现，生成可综合 RTL（Verilog）代码交付；
- **验证**：CModel 与 RTL 在同一激励下并行仿真，框架内建波形、断言、覆盖率等观测手段，实现逐周期精确对拍。

## 2. WolviC 核心概念

WolviC 用三组核心概念描述电路设计、建立验证能力：结构实体定义电路的静态形态（层次、连线、存储），逻辑动作定义电路的动态行为（组合、时序），验证探针提供对电路的观测能力。本章对核心概念进行梳理，建立概念体系。

### 2.1 结构实体：Module、Port、Wire、Reg、Mem

| 概念 | 职责 |
|---|---|
| Module | 树状层次节点：持有端口、Wire、Reg、Mem 与子模块；一个模型的全体模块构成一棵有根树，模块间只经端口交互 |
| Port | 模块边界的输入 / 输出端口，语义上是 Wire 的边界形态 |
| Wire | 组合信号：无状态，静态单赋值（SSA） |
| Reg | 寄存器：单值状态载体 |
| Mem | 存储器：按行寻址的状态阵列 |

Wire 与 Port 合称**信号**，语义为无状态的组合连线；Reg 与 Mem 合称**状态**，语义为时序存储。

### 2.2 逻辑动作：Assign、Update

逻辑动作分两类：

| 动作 | 类别 | 职责 |
|---|---|---|
| Assign | 组合逻辑动作 | 连续生效，驱动 Wire 与 Port |
| Update | 时序逻辑动作 | 事件触发，更新 Reg 与 Mem |

逻辑动作以赋值语句书写，一般形式为 `动作目标.[可选的结构段] = 表达式`。

Assign 动作的目标是 Wire 或 Port，可用受支持的运算符直接组织表达式，WolviC 框架自动提取依赖关系：

```cpp
c = a + b; // Assign: c 为 Wire 或 Port，依赖 a、b，a、b 可为 Wire、Port 或 Reg
```

为了能够高效灵活地编写行为建模代码，Assign 允许使用 lambda 表达式包裹宿主代码片段，使用with结构声明依赖：

```cpp
c.assign().with(a, b) = [](auto src) { 
    auto [a_val, b_val] = src;
    return a_val + b_val; 
};
```

Update 动作的目标是 Reg 或 Mem，必须指定触发事件（`.on(...)`）和可选的使能条件（`.en(...)`），表达式同样可以使用 lambda 表达式：

```cpp
// Update: cnt 为 Reg，依赖 cnt 和 delta，触发事件为 clk 上升沿，条件为 en
cnt.update().on(posedge(clk)).en(en) = cnt + a; 

// Update with lambda
cnt.update().on(posedge(clk)).en(en).with(cnt, delta) = [](auto src) { 
    auto [cnt_val, delta_val] = src;
    return cnt_val + delta_val;
}; 
```

### 2.3 验证探针：比对、日志、断言、波形、覆盖率

探针是挂在信号与状态上的**只读观测终端**：不改变被观测对象的语义，逻辑不得读取探针，同一实体上可挂的探针数量不限。探针在建模函数中与动作同处注册；每个探针持有全局唯一标识（层次路径 + 探针名），作为其全部输出的归属键；采样统一在状态提交完成、组合收敛之后，以时钟拍为粒度。五种探针覆盖验证的常规手段：

| 探针 | 行为 | 输出 |
|---|---|---|
| 比对探针 | 双轨验证中，行为树与可综合树的配对节点上逐拍比对同一逻辑量 | 失配报告（标识 + 拍号 + 两侧值） |
| 日志探针 | 值变化时记录（可配置每拍） | 日志流 |
| 断言探针 | 每拍对值求谓词，违例报错 | 违例报告 |
| 波形探针 | 记录值序列 | 波形文件（FST） |
| 覆盖率探针 | 累计值覆盖与翻转覆盖 | 覆盖率数据库 |

比对探针是双轨对拍的核心：两种描述形态在同一激励下并行仿真，配对探针逐拍比对，失配即时报出位置与拍号。各探针的注册形式与配置细则见后续章节。

## 3. 案例：Popcount 的两种描述形态

以 Popcount（统计位向量中 1 的个数）为例，展示同一模块的 cmodel 与 rtl 两个版本在代码上的差异。Popcount 是纯组合逻辑，两版差异以最干净的形式呈现：行为模型是一行宿主库调用，可综合模型是一棵手工搭建的加法树。

### 3.1 共享部分：接口与配置

两种描述形态共享同一份端口定义与构造配置，差异只出现在两个建模函数中：

```cpp
class Popcount : Module {
    /* 模块端口定义 */
    IN (UInt(64), in);      
    OUT(UInt(8), count);

    void cmodel() { /* 行为化建模代码 */ }
    void rtl()    { /* 可综合设计代码 */ }
};
```

### 3.2 cmodel 版本：一行宿主库调用

```cpp
void cmodel() {
    count.assign().with(in) = [](auto src) {
        auto [v] = src;
        return std::popcount(uint64_t(v));   // 宿主库调用；int 在赋值处转 UInt
    };
}
```

```cpp
class Popcount : Module {
    /* 模块端口定义 */
    IN (UInt(64), in);      
    OUT(UInt(8), count);

    void cmodel() { 
        count.assign().with(in) = [](auto src) {
            auto [in] = src;
            return std::popcount(uint64_t(in));   
            // 宿主库调用；int 在赋值处转 UInt
        }; 
    }
    void rtl()    { /* 可综合设计代码 */ }
};
```

行为描述把 popcount 当作一次宿主库调用：lambda 是黑盒，体内任意 C++；框架看不见其内部，依赖经 `.with(in)` 显式声明。

### 3.3 rtl 版本：手工加法树

```cpp
void rtl() {
    std::vector<UInt> level;                  
    // 宿主容器装记录临时量：生成期元程序
    for (int i = 0; i < width_; ++i)
        level.push_back(in[i]);               
        // 第 0 层：width_ 个 1 位值
    while (level.size() > 1) {
        std::vector<UInt> next;
        for (size_t i = 0; i + 1 < level.size(); i += 2) {
            auto w = level[i].width() + 1;    
            // 和的位宽：操作数 +1
            next.push_back(zext(level[i], w) + zext(level[i + 1], w));
        }
        if (level.size() % 2) next.push_back(level.back());   
        // 奇数直接传递
        level = std::move(next);
    }
    count = level[0];
}
```

可综合描述把 popcount 当作一棵逐层归并的加法树：没有 lambda，全部用受支持的运算符组织表达式，依赖由框架从表达式中自动提取；`std::vector` 与 `for` / `while` 是生成期执行的普通 C++ 元程序，记录期每个值都是常量，循环自然展开。

### 3.4 两版差异对照

| 维度 | cmodel 版本 | rtl 版本 |
|---|---|---|
| 表达形态 | lambda 黑盒 + `.with(...)` 显式声明依赖 | 运算符表达式，依赖自动提取 |
| 计算组织 | 一次宿主库调用，行为黑盒 | 手工搭建加法树，结构白盒 |
| 中间结果 | 无需显式组织 | 记录临时量逐层归并 |
| 位宽处理 | 宿主类型自然承载（`uint64_t`） | 定宽语义，每层 `zext` 显式扩一位 |
| 循环 | 无 | 生成期元程序，记录期展开 |
| 用途与产物 | 微结构探索、golden reference | 可综合实现，生成 Verilog 交付 |

差异的本质是分工：cmodel 回答"算什么"——以最少的代码给出周期精确的行为；rtl 回答"怎么算"——把计算展开为真实的电路结构。两版共享同一份接口，验证时在同一激励下并行仿真，端口 `count` 逐拍对拍。

## 1. 定位与核心概念

### 1.1 定位

WolviC 是基于 C++ 的建模、设计、验证一体化框架。硬件在同一份 C++ 源码中以两种描述形态给出：

- **建模**：行为描述——以完整的 C++ 表达力书写行为，面向微架构探索与 golden reference；
- **设计**：可综合描述——以受限而精确的类型与表达式描述硬件，可机械翻译为 Verilog；
- **验证**：行为 / 可综合双轨协同仿真，周期级精确；五种探针覆盖比对、日志、断言、波形、覆盖率（§6）；生成的 Verilog 再经 Verilator 后端对拍。

WolviC 的描述风格是**结构显式、行为自由**：模块的信号、状态、连接，以及每条计算"读谁、改谁"，都显式声明——框架看得见完整的数据流，因此能自动推导执行顺序、静态检查多驱动与悬空这类结构错误；而每条计算内部"具体怎么算"，保持书写自由。结构粒度停在信号与计算这一层：不下沉到比特级（那是 RTL 的事），也不丢掉依赖关系（丢了依赖，自动调度与检查就无从谈起）。

### 1.2 核心概念

概念体系包含五种结构实体与两种计算动作：

| 概念 | 类别 | 职责 |
|---|---|---|
| `Module` | 结构实体 | 树状层次节点，持有信号、状态与子模块；全体模块构成一棵有根树 |
| `IN` / `OUT` | 结构实体 | 模块边界的端口，语义上是 Wire 的边界形态 |
| `WIRE` | 结构实体 | 组合信号，无状态，静态单赋值（SSA）：恰被一条 Assign 驱动 |
| `REG` | 结构实体 | 寄存器，单值状态载体，Update 触发时整体替换次态 |
| `MEM` | 结构实体 | 按行寻址的状态阵列：读给出已提交内容；写以行为单位、在提交点生效，未写的行保持 |
| Assign | 计算动作 | 组合计算：连续生效，驱动 Wire 与端口 |
| Update | 计算动作 | 时序计算：事件触发，更新 Reg 与 Mem |

Wire 与端口合称**信号**——无状态的组合连线；Reg 与 Mem 合称**状态**——时序存储。信号与状态的类型可以是任意 C++ 类型（行为侧），也可以是可综合类型（`Bool` / `UInt` / `SInt` / `Vec` / `Bundle`，见类型系统规划）。

计算动作用赋值语句书写，右侧直接写表达式——这是基本形，依赖自动提取，不需要任何额外声明：

```cpp
sum  = a + b;                                   // Assign：驱动 Wire 或端口
cnt.update().on(posedge(clk)).en(en) = cnt + 1; // Update：更新 Reg
```

一句赋值由三部分组成：

- **目标**（赋值号左侧）：这条计算写入谁。Assign 的目标是 Wire、本模块的 Out 或子模块的 In；Update 的目标是 Reg 或 Mem（Mem 另经 `.addr(...)` 指定写入行，激活时只写该行、其余行保持）；
- **表达式**（赋值号右侧）：这条计算算什么、依赖谁——被引用的信号即依赖；默认形态可直接分析、可综合，另一种是宿主表达式（§2.2）；
- **Update 的结构段**（中段）：`.on(...)` 事件列表（必填）——任一 Bool 信号的边沿均可作事件，时钟没有特殊地位；`.en(...)` 电平守卫（可选）——守卫不满足时该 Update 不激活，状态保持。同一状态的多条 Update 同时激活时，**注册顺序即优先级**：先注册者后写并覆盖。

表达式的另一种形态是宿主表达式：右侧换成 lambda，体内任意 C++——代价是框架看不见 lambda 内部，依赖要显式声明（`.reads(...)`，实参顺序决定 lambda 收值顺序）：

```cpp
sig.assign().reads(s1, s2) = [](auto src) { /* 任意 C++ */ };
reg.update().on(posedge(clk)).en(g).reads(s1, s2) = [](auto src) { /* ... */ };
mem.update().on(posedge(clk)).addr(a).en(g).reads(s1) = [](auto src) { /* 返回写入值 */ };
```

## 2. 三段式表达：构造函数 + cmodel() + rtl()

### 2.1 动机

双轨描述下，一个模块的行为版与可综合版内部组织本就不同（队列的行为版内部是 `std::deque`，可综合版是存储阵列加头尾指针）。若把创建实体、注册动作、完成连线全部塞进构造函数这一个入口，两套注册代码只剩 if/else 分流一条路。WolviC 因此把"注册动作与连线"从构造函数移出，按描述性质分入两个建模函数；构造函数留下两项只与它相称的职责：参数化配置，以及——因为配置此时已经就绪——端口属性的补全（§2.3）。

### 2.2 总览

一个 WolviC 模块由三组成分构成：

| 成分 | 形式 | 职责 | 执行时机 |
|---|---|---|---|
| 接口 | `IN` / `OUT` 成员变量（样品形态，位宽可缺省） | 模块接口，两个建模函数共享 | 成员初始化期创建；缺省属性在构造函数内补齐，返回即冻结 |
| 参数化配置 | 构造函数 | 解析参数、补全端口属性、计算派生配置、断言合法性 | 对象构造时 |
| 建模函数 | `void cmodel()` / `void rtl()` | 创建内部实体、注册 Assign/Update、完成连线 | 建树期，按树的性质调用 |

三组成分中，两个建模函数做的是同一件事——**用表达式建模依赖关系与计算逻辑**。每条建模语句都是一句"目标 = 表达式"（恒等连接是表达式的特例，寄存器次态同理）：表达式同时声明了"算什么"（计算逻辑）与"依赖谁"（被引用的信号）。右侧的表达式有两种写法：

| 形态 | 框架可见性 | 依赖来源 | 仿真期求值 | 可综合 |
|---|---|---|---|---|
| **表达式**（默认形态）：白名单算子作用于可综合类型，记录为表达式 DAG | 可见全部结构 | 从 DAG 自动提取，精确到叶子 | 解释执行 | 是 |
| **宿主表达式**：lambda 黑盒，体内任意 C++ | 不可见内部 | 显式 `.reads(...)` 声明 | 直接执行 | 否 |

- `rtl()` 只用表达式——可综合的前提是可分析（§2.5）；
- `cmodel()` 以宿主表达式为常态——宿主表达力正是行为建模的价值；表达式同样合法（它是宿主语言的子集，依赖同样自动提取）；
- lambda 即宿主表达式——宿主行为的黑盒形态：只在需要宿主表达力时使用，可分析的部分都应用表达式直接书写；
- 裸宿主语句不是建模语句（`dout = q.front()` 在记录期就求值了）：宿主计算必须提升为仿真期可求值的形式——包进 lambda，或改写为表达式；
- 比对探针（observe，§6.3）的摘要 lambda 不受此约束：它是观测，不建模逻辑。

最小案例——固定位宽的加法器，只写 `rtl()` 即同时覆盖建模与设计，连构造函数都不用写：

```cpp
struct Adder32 : Module {
    IN (UInt(32), a);        // 声明时给足位宽
    IN (UInt(32), b);
    OUT(UInt(32), sum);

    void rtl() {
        sum = a + b;         // 端口是成员，直接使用（注册链见 §1.2）
    }
};
```

三条规则：

1. `cmodel()` 与 `rtl()` **至少定义一个**；全缺是建模错误（检测机制见 §7）。
2. 构造函数做两件事：**参数化配置 + 端口属性补全**；返回时全部端口必须已定型（§2.3 的对账），返回后端口冻结。动作注册与连线仍然只在建模函数中完成。
3. 两个建模函数共享同一份端口成员与同一份配置——接口一致性是构造性的。

### 2.3 构造函数：参数化配置 + 端口属性补全

- 可做：接收构造参数、**补全端口的缺省属性（位宽）**、计算派生配置、断言参数合法性，结果存为普通数据成员；
- 不可做：增删端口（成员集合编译期固定）、创建内部实体、注册动作、连线——建模上下文此阶段尚未进入，注册接口不可用（强制方式见 §7）。

#### 位宽：声明可缺省，构造可补齐，返回必对账

`UInt` 是普通（非模板）类：位宽不进类型系统，而是端口实体的运行期属性。由此声明与配置可以分离：

```cpp
struct Adder : Module {
    IN (UInt(), a);            // 位宽缺省：UInt() 表示"待配"
    IN (UInt(), b);
    OUT(UInt(), sum);

    explicit Adder(int width) {
        a.setWidth(width);     // 构造函数内补齐
        b.setWidth(width);
        sum.setWidth(width);
    }   // 返回时对账：三个端口必须都已定型
};
```

规则：

- **"需要位宽"是类型的属性**：`UInt` / `SInt` 需要；`Bool`、宿主类型（`std::vector<int>` 等）没有位宽概念，声明即完整——不需要配置的类型永远不必提位宽；
- 位宽可以**声明时给足**（`IN(UInt(8), a)`），也可以**声明缺省、构造函数补齐**（`IN(UInt(), a)` + `a.setWidth(w)`），也可以**声明给默认、构造期覆盖**——构造期同一属性允许多次写入，后者为准（last-write-wins）；冻结后对账只查完整性（每个待配属性有值），不查重；
- **对账在构造函数返回时**：凡需要位宽而仍未定型的端口，报错并附层次路径（如 `port 'top.queue.din' (UInt) requires width but none was configured`）。检查时机：子模块在 `MOD` 语句返回时（其构造函数已结束），根模块在 `elaborate()` 时——全部先于任何仿真；
- `setWidth` 只存在于有位宽属性的实体类型上——给 `Bool` 端口调 `setWidth` 是编译期错误；位宽值非法（≤ 0、超上限）在设置点报运行期错误；
- 表达式两侧的位宽一致性（定宽回绕语义的要求，RTL 规划 §2）在**创建期 / 记录期 / elaborate 期**检查，报错附层次路径——与多驱动、悬空同级。编译期检查被放弃是刻意的：位宽来自构造参数，表达式两侧的位宽在编译期无从得知；
- 值字面量（"8 宽的 42"）的书写形态另议（§7）；
- 模板回归本职：编译期代码生成（`if constexpr` 选实现、生成 N 份同构结构），不再用于传位宽。

#### 数量：Vec 聚合端口

运行期数量的端口经**可综合的 Vec 类型**实现——元素数量与位宽一样，是样品携带的运行期属性：

```cpp
struct Mutex : Module {
    IN (Bool(),      clk);
    IN (Vec(Bool()), req);             // 元素类型编译期确定；长度缺省
    OUT(Vec(Bool()), gnt);

    explicit Mutex(int n) {
        req.setSpec(Vec(Bool(), n));   // 构造函数内补齐长度
        gnt.setSpec(Vec(Bool(), n));
    }   // 返回时对账：长度必须已定型
    // ...
};
```

- 声明时给足形态是 `Vec(UInt(8), 4)`（元素样品 + 数量）；长度与元素位宽可按属性分别缺省（`Vec(Bool())` 只缺长度、`Vec(UInt())` 都缺），补全时给足完整样品、已定型属性须一致；**元素类型不可缺省**——`Vec()` 形态不存在（"是什么"进类型系统、"是多少"进运行期属性，详见类型系统规划 §8）；
- 对账规则与位宽相同且递归：构造函数返回时，Vec 的数量与元素样品都必须定型；
- Vec 端口是**一个实体**：整体驱动（SSA 照旧）；元素访问 `req[i]`——常量下标免费，动态下标在 rtl 侧生成 mux 树（RTL 规划 §2）；元素级独立驱动的需求出现时再评估（§7）；
- 与 Mem 的分工不变：Vec 是整体读写的聚合值；Mem 是按行寻址、逐行提交的状态阵列。纯行为模块的聚合端口继续用宿主容器（`std::vector` 等），Vec 是可综合侧的类型。

### 2.4 cmodel()：行为模型——lambda 黑盒

`cmodel()` 提供完整的行为建模能力：

- lambda 是黑盒：体内任意 C++——`std::sort`、`std::deque`、宿主库调用均可；宿主计算必须包进 lambda——裸宿主语句在记录期就求值了，不是建模语句（§2.2）；
- 表达式同样合法——`sum = a + b` 直接记录 DAG、依赖自动提取，与 `rtl()` 同机制；行为建模的常态仍是 lambda：宿主表达力正是这一侧的价值；
- 信号与状态的类型参数任意：`std::vector`、STL 容器、用户自定义类均可；
- 端口是成员变量，建模函数内直接使用——无字符串、无类型重述；
- 用途：快速建模、golden reference。

接口约束（细则见 RTL 规划 §2，待并入）：模块若提供 `rtl()` 侧，其端口类型必须可综合——同一组端口值要在行为树、可综合树、Verilated 模型之间机械传递。纯行为模块（永不进入可综合世界）不受此限。

### 2.5 rtl()：可综合模型——连接与表达式，没有 lambda

`rtl()` 与 `cmodel()` 共享同一套实体、动作与结构段（§1.2），但**建模语句的表达式形态受限**——`rtl()` 里没有 lambda。每条语句是**连接**或**表达式**：

```cpp
void rtl() {
    empty_w = tail == head;                                // 表达式：驱动 Wire
    empty   = empty_w;                                     // 连接：恒等
    dc.valid = en && !full;                                // 叶子驱动（粒度规则见类型系统规划 §6）
    head.update().on(posedge(clk)).en(do_deq) = head + 1;  // 表达式次态
}
```

- **读集概念在 rtl 消失**：依赖从表达式 DAG 自动提取，精确到叶子——比 `cmodel()` 的显式读集更准，也不可能写错（"声明与实读不符"的审计问题在 rtl 侧不复存在）；
- 多行逻辑用**局部记录临时量**（`auto t = a + b;`）与具名 Wire 分解；配置、静态分支、循环就是普通的 C++ 元程序，记录期执行——没有 lambda 就没有捕获，"捕获只允许宿主常量"的规则随之消解；
- 两侧之别由此定型（表达式的两形态，§2.2）：`cmodel()` 以黑盒 lambda + 显式读集为常态（仿真期执行，任意 C++；表达式同样合法）；`rtl()` 只用表达式——连接与表达式 DAG（记录期构建，仿真期解释，翻译为 Verilog）；
- 例外：比对探针（observe）的摘要 lambda 在两侧都保留（任意 C++——它是观测，不是逻辑）。

两个限制（细则见 RTL 规划 §2，待并入本系列）：

1. **数据类型受限**：`Bool`、`UInt`、`SInt`、Bundle、Vec——具有确定形状的硬件类型（位宽、长度在创建期给定，见 §2.3）；原生整型可声明端口与状态，但参与生成 RTL 的运算必须经 `UInt`/`SInt` 进行。
2. **操作受限**：白名单即 `UInt`/`SInt` 类型库的 API 面（算术、位运算、比较、`mux`、位操作、归约）；三条形态约束——数据相关的分支只有 `mux()`、循环必须静态有界、普通函数调用自由（记录期自然内联）。

### 2.6 合法性：至少一个建模函数

| 定义情况 | 模块性质 | 行为树中 | 可综合树中 |
|---|---|---|---|
| 仅 `cmodel()` | 纯行为模块 | `cmodel()` | 以行为侧出现（所在子树不再完全可综合，不进 RTL） |
| 仅 `rtl()` | 可综合模块 | `rtl()` 原生解释仿真兜底（结构更细，慢一点） | `rtl()` |
| 两者皆备 | 双模模块 | `cmodel()`（取其快） | `rtl()`（取其真） |
| 两者皆缺 | 建模错误 | — | — |

"至少一个"在 elaborate 期必查，报错附模块类名；编译期强化（CRTP + concept 的 static_assert）列为待定方向（§7）。

## 3. 实体归属：端口是成员，内部实体默认局部

### 3.1 规则

| 实体 | 归属 | 说明 |
|---|---|---|
| `IN` / `OUT` | **必须是成员变量**（样品形态，位宽可缺省） | 接口是两个实现共享的公共契约 |
| `WIRE` / `REG` / `MEM` / `MOD` / 数组 | **默认是建模函数的局部变量**；确有跨阶段访问需求仍可绑为成员 | 内部结构是单侧私有 |

- **端口必须成员**：两个实现共享同一份接口定义——它们就是类的同一组成员端口，一致性是构造性的；仿真期端口被外部 `set`/`get`、被父模块跨边界读写，需要对象级可访问性。位宽的可缺省性由"位宽是运行期属性"（§2.3）支撑，与成员形态无冲突；
- **内部实体默认局部**：它们在两个实现中本就不同（`deque` vs 阵列加指针），没有共享基础；建模期之外也没有谁需要引用它们——**值由框架持有的仿真状态承载，动作经读集与表达式取值，句柄本身不用于实际计算**。确有构造后访问需求（如 testbench dump 内部状态）仍可绑为成员——规则因此是"默认局部、按需成员"。

一个推论（双模模块慎用成员内部实体）：成员实体在两侧都存在——成员 Wire 只在一侧被驱动时，另一侧展平后会报悬空；成员 Reg/Mem 虽不检查驱动数，却恒为初值，多半不是本意。因此双模模块的内部实体应一律局部化。（成员内部实体的属性补全遵循与端口相同的对账规则：构造函数返回时必须已定型。）

### 3.2 端口即成员：无取用层

端口就是成员变量，建模函数、连线、顶层驱动全部直接使用，没有中间层：

```cpp
void cmodel() {
    REG(DQ(), q);
    q.update().on(posedge(clk)).reads(q, enq, din) = [](auto src) { /* ... */ };
    dout.assign().reads(q) = [](auto src) { /* ... */ };
}
```

```cpp
Queue top(8, 12);
top.elaborate();
top.enq.set(1);          // 顶层驱动见 §5.4
top.eval();
```

端口实体的连线权限规则见 §3.4，注册链见 §1.2。

### 3.3 内部实体：样品形态的局部声明

内部实体经 `WIRE` / `REG` / `MEM` / `MOD` 宏声明，统一为样品约定——**首参是样品值，名字永远在末位**（`MEM` 的名字之前另有行数）：

```cpp
void cmodel() {
    REG(DQ(), q);                    // 行为侧：样品即空容器，类型取自样品类型
}

void rtl() {
    REG(UInt(width_), cnt);          // 位宽随样品给足——构造参数直达声明
    MEM(UInt(width_), kMaxN, ram);
    WIRE(Bool(), empty_w);           // 无位宽概念的类型：空样品
    REG(UInt(kPtrW), head);          // 固定位宽也只是一个字面量样品
}
```

- **类型取自样品的类型，运行期属性（位宽）取自样品的值**；样品在声明位置是类型描述物——其承载的数值内容被忽略（`UInt(8)` 读作"宽度 8 的 UInt"，不是"值 8"）；
- 宏展开为一句引用声明（`auto& cnt = createReg("cnt", UInt(width_));`）：实体由框架持有，名字由宏自动字符串化，创建期命名查重，层次路径照常拼出；
- 样品与实体错配在**编译期**被拒：`Bool` 的构造不接受位宽；位宽值非法在创建期报运行期错误，附层次路径；
- 局部实体同样可以缺省后补（`REG(UInt(), cnt)` + `cnt.setWidth(w)`）——对账点是声明它的建模函数返回时，与端口的"构造函数返回时"同一条原则：**创建作用域结束，必须定型**；
- 样品须可廉价构造；不可默认构造的宿主类型用 `Type<T>` 标签逃逸（拼写待定，§7）；
- 建模函数返回后句柄离开视野，实体与动作已由框架持有——这正是"只用于声明结构，不用于实际计算"的含义。

### 3.4 子模块与连线

子模块经 `MOD` 宏创建，构造参数透传；连线限定三种模式，都在父模块的建模函数中以普通 Assign 完成：

- **下行**：父模块驱动子模块的 In（`sr.din = sorted`）；
- **上行**：父模块读子模块的 Out（`dout = sr.dout`）；
- **兄弟子模块间**：由前两种组合而成——父模块读一个子模块的 Out、驱动另一个的 In，无需专门的连线设施。

端口权限三条规则：子模块的 In 由父模块驱动、子模块内只读；子模块的 Out 供父模块读取；父模块只能读写**直接**子模块的端口，不越级访问。

```cpp
void cmodel() {
    REG(Vec(), sorted);
    MOD(SR, sr, SR::Cfg{3});               // 局部子模块句柄；构造参数透传

    sorted.update().on(posedge(clk)).reads(din) = [](auto src) { /* ... */ };
    sr.din = sorted;                       // 下行：本模块 Assign 驱动子模块 In
    sr.clk = clk;                          // 时钟分发同理
    dout   = sr.dout;                      // 上行：读子模块 Out
}
```

调用时序：`MOD` 语句处运行子模块的构造函数（参数化配置完成、端口定型并对账，连线语句即刻可写）；子模块自己的建模函数由框架随后按当前树的性质调用——行为树调 `cmodel()`、可综合树调 `rtl()`、缺侧按 §2.6 兜底。

建模函数是普通成员函数：注册只是收集声明、不做求值，循环、条件分支、辅助函数、工厂方法都可以自由组织注册代码。

### 3.5 共享构建逻辑

两个建模函数同在一个类里，共享常量、配置成员、辅助函数与子模块工厂：

```cpp
struct Crossbar : Module {
    explicit Crossbar(int n) { /* 端口补全等 */ }
private:
    int ceilLog2(int n) const;                     // 两侧都用的辅助函数
    template <class M> M& makeArbiter(/* ... */);  // 两侧都调用的子模块工厂
};
```

"层次写两次"的顾虑由此消解：重复被压进函数体内的差异部分。共享的创建语句同时是双树配对的主要来源——两侧经同一 MOD 语句（含共享 helper）创建的子模块自动成对，其下的比对探针按名匹配（§6.3）。

## 4. 完整案例：双模 Popcount

统计一个位向量中 1 的个数——行为模型是一行宿主库调用，可综合模型是一棵手工搭建的加法树。纯组合模块里，两轨差异以最干净的形式呈现：

```cpp
struct Popcount : Module {
    // ── 接口：端口是成员变量；位宽缺省，构造函数补齐 ──
    IN (UInt(), in);
    OUT(UInt(), count);

    // ── 构造函数：参数化配置 + 端口补全；返回时对账 ──
    explicit Popcount(int width) : width_(width) {
        assert(width_ > 0 && width_ <= 64 && "Popcount: bad width");
        in.setWidth(width_);
        count.setWidth(ceilLog2(width_ + 1));     // 0..width 需要这么宽
    }   // 返回时：两个端口均已定型

    // ── 行为模型：lambda 是黑盒，任意 C++ ──
    void cmodel() {
        count.assign().reads(in) = [](auto src) {
            auto [v] = src;
            return std::popcount(uint64_t(v));    // 一行宿主库调用；int 在赋值处转 UInt
        };
    }

    // ── 可综合模型：没有 lambda——记录表达式搭加法树 ──
    void rtl() {
        std::vector<UInt> level;                  // 宿主容器装记录临时量：元程序
        for (int i = 0; i < width_; ++i)
            level.push_back(in[i]);               // 第 0 层：width_ 个 1 位值
        while (level.size() > 1) {
            std::vector<UInt> next;
            for (size_t i = 0; i + 1 < level.size(); i += 2) {
                auto w = level[i].width() + 1;    // 和的位宽：操作数 +1
                next.push_back(zext(level[i], w) + zext(level[i + 1], w));
            }
            if (level.size() % 2) next.push_back(level.back());   // 奇数直接传递
            level = std::move(next);
        }
        count = level[0];                         // 赋值对账：位宽须一致
    }

private:
    int width_;           // 普通数据成员：配置，不是信号
};
```

逐点说明：

- **反差即定义**：行为侧把 popcount 当作一次宿主库调用；可综合侧把它当作一棵逐层归并的加法树——这不是风格差异，是"行为黑盒 vs 结构白盒"的定义差异；
- **rtl 侧全是普通 C++ 元程序**：`std::vector` 装的是记录临时量，`while` / `for` 在记录期正常执行；每层位宽由 `level[i].width()` 这个宿主侧查询驱动——生成期每个值都是常量，循环自然展开（"循环静态有界"天然满足）；
- **`zext` 显式扩位**：定宽回绕语义下 `w + w` 仍是 `w` 位，进位会丢——加法树每层显式扩一位（白名单规则，RTL 规划 §2；`zext` 的具体拼写随白名单清单定稿）；
- **位宽对账在两端**：构造函数里 `count.setWidth(ceilLog2(width_ + 1))` 是声明侧的承诺；`count = level[0]` 赋值处检查加法树的实际结果位宽——不一致即报错附层次路径；
- 无状态、无内部实体、无比对探针——对拍由端口值直接承担（`count` 是可综合族，两树机械比对）。带状态与比对探针（observe）的完整案例见 RTL 规划 §0（Queue 示例）。

## 5. 模式、建图与仿真

### 5.1 三种模式

| 模式 | 建树 | 各节点调用 | 用途 |
|---|---|---|---|
| 纯行为 | 一棵行为树 | `cmodel()`，缺侧以 `rtl()` 解释仿真兜底 | 微架构探索 |
| 验证 | 行为树 + 可综合树（+ RTL 后端） | 各调各的；配对节点比对探针逐拍对拍 | 双轨验证 |
| 生成 | 完全可综合子树 | `rtl()` 以记录模式执行 → Verilog | 设计交付 |

构造函数在每棵树中都运行一次（两树各持一份模块实例），端口补全也随之各执行一次——同一构造参数保证两树接口一致。模式选择的用户接口待定（§7）。

### 5.2 生命周期与建图

| 时期 | 内容 |
|---|---|
| **建树** | 模块构造（构造函数：参数化配置与端口补全）与建模函数调用（创建实体、注册动作、连线）交错进行——`MOD` 语句处子模块构造，其建模函数由框架按树的性质随后调用。注册只是收集声明，不做任何求值 |
| **建图** | 模块树展平为平面的实体集与动作集（动作内的层次引用重定向到扁平实体），做结构合法性检查，建仿真图；返回后结构冻结 |
| **仿真** | `set()` / `eval()` / `get()` 驱动与读取，产生信号与状态的值序列 |

结构合法性检查在展平后的扁平集合上进行：

- 每个信号恰有一条驱动 Assign（SSA）；端口同样适用——子模块的 In 由父模块驱动、Out 由子模块内部驱动；
- 无悬空：除根模块的 In（由外部驱动）外，每个信号都有驱动者；
- Reg 与 Mem 不检查驱动数——它们由 Update 更新，天然允许多条（§1.2）。

### 5.3 仿真时间模型（摘要）

一次 `eval()` 由若干 **round** 构成，每个 round 固定两阶段：

1. **组合求值**：全部动作按依赖序执行——Assign 求值并写入目标；Update 只记录次态与激活标记（边沿命中 ∧ 使能），不触碰任何状态。由此，凡读取状态的地方，读到的必是本轮写入前的值；
2. **状态更新**：激活的 Update 按优先级链提交（先注册者后写并覆盖），全部写入在同一时刻生效（NBA）。

阶段二若有任何状态被更新，新值自下一 round 起可见，可能构成新的边沿（级联时钟由此在同一 `eval()` 内逐级推进），于是进入下一 round；若没有任何状态更新，`eval()` 返回。边沿检测在组合求值阶段进行：Update 对自己事件列表中的 Bool 信号逐个与旧值比较，0→1 为上升沿，反之为下降沿。组合环经迭代求稳态，设趟数上限，不收敛（振荡）报错并附环路径。引擎实现细则见《Wolvicmod仿真引擎规划》。

### 5.4 根模块用法

```cpp
Popcount top(16);        // 构造：参数化配置，端口补全
top.elaborate();         // 根模块对账 + 建树收尾 + 建图；此后结构冻结
top.in.set(0x00F0);      // set() 只改输入，不推进仿真
top.eval();              // 收敛到当前输入对应的稳态后返回
assert(top.count.get() == 8);
```

时钟是普通的 Bool 输入，每次跳变对应一次 `eval()` 调用——时钟在模型内没有特殊地位，任何 Bool 信号都可用作 Update 的边沿事件；先连续 `set()` 多个输入、再调一次 `eval()` 是合法用法。双树构建、两遍编译、RTL 生成的详细语义见《Wolvicmod RTL生成规划》（待并入本系列）；探针与对拍见 §6。

## 6. 验证与探针

### 6.1 验证能力

WolviC 的验证建立在同一份源码的两种描述形态（§2）之上：

- **双轨协同仿真**：行为树与可综合树在同一激励下并行推进——行为模型是 golden reference，可综合模型是被测实现；
- **周期级精确**：观测与比对的粒度是时钟拍，与 RTL 的拍界对齐；
- **探针系统**：五种探针覆盖验证的常规手段——比对、日志、断言、波形、覆盖率；
- **后端对拍**：生成的 Verilog 经 Verilator 仿真，与 C++ 侧再对一轮（细则暂载 RTL 规划）。

### 6.2 探针的一般形式

五种探针共享统一的注册形态与语义：

- **监听对象**：WIRE 与 REG——端口语义上是 Wire（§1.2），同样可挂。探针是**只读的观测终端**：不改变被监听对象的语义，逻辑不得读取探针；在动作依赖图中探针恒为汇点，挂在同一信号上的探针数量不限；
- **注册点**：建模函数（`cmodel()` / `rtl()`）中注册，与动作同处——内部实体是建模函数的局部变量，对内部实体的探针只能在此注册。探针实体由框架持有，建模函数返回后句柄离开视野。根模块端口的探针也可由 testbench 在 `elaborate()` 前从外部注册（实体引用 + 探针名）；
- **全局唯一标识符**：每个探针持有全局唯一标识——层次路径 + 探针名（如 `top.queue.occupancy@wave`），注册期查重，冲突即报错附路径。标识符是所有探针输出（波形文件、日志流、覆盖率数据库、失配报告）的归属键，也是运行期开关与过滤的句柄；
- **采样时机**：统一在 round 末采样（状态提交完成、组合已收敛——采到的是该 round 的稳定值）；以拍为粒度的探针（比对、断言、覆盖率）按拍界归并。多时钟域的采样语义待定（§7）；
- **开关**：探针可按类别或标识符在运行期过滤；编译期可整体剥除（开关拼写待定，§7）。

### 6.3 五种探针

| 探针 | 触发 | 行为 | 输出 |
|---|---|---|---|
| 比对探针 | 每拍 | 双侧采样同一逻辑量，逐拍比对 | 失配报告（标识符 + 拍号 + 两侧值） |
| 日志探针 | 值变化（可配置每拍） | 记录旧值→新值 | 日志流 |
| 断言探针 | 每拍（或值变化） | 谓词求值，违例报错 | 违例报告（标识符 + 拍号 + 当前值） |
| 波形探针 | 每 round（值变化即记） | 记录值序列 | 波形文件（FST） |
| 覆盖率探针 | 每拍 | 累计值覆盖与翻转覆盖 | 覆盖率数据库（可合并） |

注册形态（拼写为提案，细则待定）：

```cpp
void rtl() {
    REG(UInt(kPtrW), head);
    WIRE(Bool(), empty_w);
    // ... 逻辑注册 ...

    observe(head, "head");                                  // 比对探针：双树按名配对
    logProbe(empty_w, "empty");                             // 日志探针：值变化时记录
    assertProbe(head, "head_in_range",                      // 断言探针：谓词为假即违例
                [](auto h) { return h < kMaxN; });
    waveProbe(empty_w, "empty");                            // 波形探针：值序列入 FST
    covProbe(head, "head_cov");                             // 覆盖率探针：值覆盖 + 翻转覆盖
}
```

逐探针说明：

- **比对探针（原 observe）**：双轨验证的核心。挂在行为树与可综合树的**配对节点**上——两侧经同一 `MOD` 语句创建的子模块自动成对，其下探针按名匹配。监听值直接比对（可综合类型按位比对；宿主类型经 `operator==`）；内部状态的比对经**摘要 lambda** 折算为可比对的摘要值——lambda 体内任意 C++（观测不是逻辑，不受表达式形态约束，§2.2）。失配即报错，附标识符与拍号；
- **日志探针**：监听值变化（默认）或逐拍记录；可带格式 lambda 定制行内容（签名待定，§7）；
- **断言探针**：对监听值每拍求谓词，谓词是宿主 lambda（任意 C++）。违例时的动作（报错继续 / 中断仿真）待定（§7）；
- **波形探针**：值序列输出 FST。可波形化按类型判定：`Bool` / `UInt` / `SInt` 内建；复合类型默认不出现，经字段引出 lambda 拆出可波形化的字段（`waveProbe(dc, "dc.valid", [](auto& b){ return b.valid; })`）；
- **覆盖率探针**：统计**值覆盖**（已见值 / 值域，可配 bins）与**翻转覆盖**（每位 0→1、1→0 的次数）；bins 的定义方式待定（§7）。

### 6.4 探针与表达式形态

探针的摘要 / 格式 / 谓词 lambda 是观测代码，不是逻辑——在 `cmodel()` 与 `rtl()` 两侧都允许任意 C++，不受表达式形态约束（§2.2）。探针只读取实体的**值**、不参与驱动，因此：

- 探针不产生多驱动，不参与 SSA 检查；
- 探针不影响可综合性——`rtl()` 侧的探针在 RTL 生成时被剥除（断言探针可选生成为 SVA，待定 §7）。

### 6.5 双轨对拍流程（摘要）

验证模式下的生命周期（细则暂载 RTL 规划 §4，待并入）：

1. **建树**：行为树与可综合树分别构建，两侧经同一 `MOD` 语句（含共享 helper）创建的子模块自动成对；
2. **配对**：两树配对节点上的比对探针按名匹配，形成逐拍比对点；
3. **推进**：同一激励驱动两树，逐拍比对全部比对探针；
4. **定位**：失配即时报出标识符与拍号——标识符的层次路径直接给出失配位置。

## 7. 待定细节

1. **建模函数的存在性检测与调用机制**：倾向 CRTP（`Module<Derived>`）+ concept，在 elaborate 期 `static_assert`"至少定义一个"；备选是基类空虚函数 + 覆写检测。树的性质如何传入、两棵树的构建与 elaborate 编排，同 RTL 规划 §9-6 一并敲定。
2. **建模函数的可见性**：public，还是 private + friend 框架入口。
3. **阶段强制的两个方向**：构造函数内误用注册接口报错（注册上下文检查语义反转）；构造函数返回后 `setWidth` 等补全接口报错（端口冻结）。
4. **局部句柄误用防护**：局部引用被拷贝存储、建模函数返回后继续使用——能否诊断、如何诊断。
5. **模式选择的用户 API**：`elaborate()` 参数、构建开关，还是独立入口。
6. **样品形态细则**：不可默认构造类型的 `Type<T>` 逃逸拼写；Bundle 样品的形态（字段位宽如何进样品）；`MOD` 变参透传的宏形态；`MOD_ARRAY` 的样品化参数序。~~补全接口按类型的划分~~（已定：统一为 `setSpec`，`setWidth` 是 `UInt`/`SInt` 的语法糖——类型系统规划 §9）。
7. **对账机制细则**：类型的"待配属性"如何声明（类型 traits）；~~重复定型报错~~已定——构造期允许覆盖（声明值即默认，后写为准）；残留：若配置事故频发，再引入 `setDefault` / 权威写入分级；局部实体的对账点（建模函数返回）与端口（构造函数返回）的统一实现。
8. **`UInt` 的值实现**：运行期位宽位向量——≤64 位内联 `uint64_t` + 位宽字段，超宽走堆；与原生整型的存储兼容关系（RTL 规划 §2 的原生整型条款）；记录模式下的操作轨迹表示。
9. **字面量与常量语法**：值 + 位宽的书写形态（与样品构造 `UInt(width)` 的区分——声明位置只有样品语义，值位置需要专门形态）；表达式中宿主整型常量（`h + 1`、`t - h >= lim`）的位宽规则——候选是按对端位宽折叠，记录期检查值可容。
10. **Vec 细则**：元素访问的命名与波形形态（`top.req[3]`）；Verilog 生成时映射为扁平位向量还是 SV 数组；Vec 的值实现（运行期长度、元素均匀）；整体 SSA 是否够用（元素级独立驱动需求出现时再评估）。
11. RTL 规划 §9 的残留项（两遍编译编排、语义边界、层次策略、纯 RTL 模式等）暂载于该文，并入本系列时一并处理。
12. **探针细则**：Mem 的监听形态（整体 / 按行 / 变更行）；多时钟域的采样与拍界归并；编译期剥除开关拼写与运行期过滤 API；断言违例动作（报错继续 / 中断仿真）；覆盖率 bins 的定义语法；日志格式 lambda 的签名；比对探针摘要类型的共享头问题（承 RTL 规划 §9）；断言探针生成 SVA 的可行性；探针注册宏拼写（一族 `PROBE` 还是按探针分立）。

## 附录 A：与 Wolvicmod 的对照与迁移

本附录是非规范内容，仅供既有 Wolvicmod 用户参考。Wolvicmod 是 WolviC 的前身——显式结构行为建模框架（结构显式声明、行为黑盒保留），解决单纯的**建模**问题；WolviC 在其概念基础上扩展可综合描述与双轨验证，覆盖建模 / 设计 / 验证三段。Wolvicmod 的全部核心抽象（七种概念、注册链、连线三模式、建图与仿真语义）由本文 §1、§5 直接定义。

| 维度 | Wolvicmod | WolviC |
|---|---|---|
| 定位 | 行为建模框架 | 建模 / 设计 / 验证一体化 |
| 建模入口 | 构造函数 | `cmodel()` / `rtl()`，至少其一 |
| 构造函数职责 | 创建实体、注册动作、连线 | 参数化配置 + 端口属性补全 |
| 端口 | `IN` / `OUT` 成员变量（类型在宏首参） | `IN` / `OUT` 成员变量（样品形态），位宽可缺省、构造函数补齐，返回时对账 |
| 端口形状参数化 | 模板（编译期） | 构造参数（运行期）：位宽经 `UInt` 样品、数量经 `Vec` 样品 |
| WIRE/REG/MEM/MOD | 强制成员（数组已可局部） | 默认局部，按需成员 |
| 创建接口形态 | `REG(T, name)`，类型在宏首参 | 样品形态：`REG(UInt(width), cnt)`、`REG(DQ(), q)`，任意 C++ 类型 |
| RTL 类型 | —（RTL 规划拟用 `UInt<N>` 模板） | `UInt` / `SInt` 普通类，位宽是实体的运行期属性 |
| 建模语句形态 | 注册链 + lambda（`.reads(...) = lambda`），快速路径为糖 | 统一载体是表达式（依赖 + 计算）；形态分化：`cmodel()` 以宿主表达式（lambda 黑盒 + 显式读集）为常态；`rtl()` 只用表达式——依赖从表达式 DAG 自动提取、精确到叶子（比对探针两侧保留 lambda） |
| 注册链 / 建图 / 仿真语义 | 框架规划 §3–§5 | 同一套语义（本文 §1.2、§5 直接定义）：`cmodel()` 全形；`rtl()` 仅表达式/连接形，`.on` / `.en` / `.addr` 等结构段不变 |

迁移一个既有 Wolvicmod 模块的机械步骤：

1. 端口与实体的宏声明改为样品形态（`IN(Vec, din)` → `IN(Vec(), din)`）；
2. 构造函数体内的注册与连线代码整体移入 `cmodel()`；
3. 成员 WIRE/REG/MEM/MOD 声明移入 `cmodel()` 成为局部（确有构造后访问需求的保留成员）；
4. 构造函数只留参数处理与端口属性补全。
