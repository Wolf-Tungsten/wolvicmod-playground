# Wolvicmod RTL 生成规划（草案）

> 状态：草案 v1（经一轮结构重组），随讨论逐步细化。本文梳理"行为描述 / 可综合描述"双轨方案的总体思路；各节中的开放问题集中在 §9，待逐个敲定。

## 0. 模块定义示例：一个类、两个版本

```cpp
// 一个队列模块：同一个类，行为版与可综合版两个成员函数
struct Queue : Module {
    // ── 公共接口：IN/OUT 是成员变量，类型必须可综合（§2 接口规则）──
    IN(Bool,     clk);
    IN(Bool,     enq);
    IN(Bool,     deq);
    IN(UInt<8>,  din);
    OUT(UInt<8>, dout);
    OUT(Bool,    empty);
    OUT(Bool,    full);

    // 两侧共享：参数、辅助函数、摘要类型（§5 规则 2 的红利）
    static constexpr int N = 16;
    struct Occ {                                  // observe 摘要：可比对、可打印（§4.1）
        uint32_t n, head;
        bool operator==(const Occ&) const = default;
    };

    // ── 行为版：任意 C++，追求表达力 ──
    void behavioral() {
        using DQ = std::deque<uint32_t>;          // 类型含逗号，先取别名再进宏
        REG(DQ, q);                               // 局部实体，不是成员（§5 规则 2）

        q.update().on(posedge(clk)).reads(q, enq, deq, din) = [](auto src) {
            auto [q, en, de, d] = src;
            auto nq = q;
            if (de && !nq.empty())   nq.pop_front();
            if (en && nq.size() < N) nq.push_back(uint32_t(d));
            return nq;                            // 任意宿主类型、任意 C++
        };
        dout.assign().reads(q)  = [](auto src) { auto [q] = src; return UInt<8>(q.empty() ? 0 : q.front()); };
        empty.assign().reads(q) = [](auto src) { auto [q] = src; return q.empty(); };
        full.assign().reads(q)  = [](auto src) { auto [q] = src; return q.size() >= N; };

        observe("occ").reads(q) = [](auto src) {          // 行为版自己的信号组
            auto [q] = src;
            return Occ{ uint32_t(q.size()), q.empty() ? 0u : q.front() };
        };
    }

    // ── 可综合版：受限写法（§2），可生成 RTL；内部组织完全不同 ──
    void synthesizable() {
        MEM(UInt<8>, N, ram);                     // 存储阵列 + 头尾指针
        REG(UInt<5>,  head);                      // 位宽由 N 经 constexpr 算出
        REG(UInt<5>,  tail);
        WIRE(Bool,    empty_w);
        WIRE(Bool,    do_deq);

        empty_w.assign().reads(tail, head) = [](auto src) {
            auto [t, h] = src; return t == h;
        };
        empty  = empty_w;                         // 恒等连接快速路径
        do_deq = deq && !empty_w;                 // 白名单内的运算（§2）
        head.update().on(posedge(clk)).en(do_deq).reads(head) = [](auto src) {
            auto [h] = src; return h + 1;         // 定宽回绕
        };
        // …tail 自增、ram 写口、dout 组合读、full 同理

        observe("occ").reads(tail, head, ram) = [](auto src) {  // 同名同型，信号组不同
            auto [t, h, m] = src;
            return Occ{ uint32_t(t - h), uint32_t(m[h]) };
        };
    }
};
```

示例要点：

- **接口是成员、内部是局部**：IN/OUT 作为成员变量两侧共享；WIRE/REG/MEM 在各侧函数体内以局部实体创建——行为版内部是 `std::deque`，可综合版是存储阵列加头尾指针，互不可见；
- **observe 同名同型、信号组各自**：两侧的 `"occ"` 配成一对（§4.3），摘要层面等价即可，内部组织随意；
- **共享逻辑写一次**：参数 `N`、摘要类型 `Occ`、以及可能共用的子模块工厂，都在类作用域共享；
- **模式决定调用谁**（§8）：纯行为模式只调 `behavioral()`；验证模式建两棵树，各调各的，observe 逐拍对拍；可综合版还能生成 Verilog（§3）。

## 1. 核心区分：行为描述与可综合描述

Wolvicmod 现有能力（见[《Wolvicmod框架规划》](Wolvicmod框架规划.md)）构成**行为描述**：结构显式声明，行为黑盒保留——lambda 体内是任意 C++，信号与状态的类型参数可以是任意宿主类型。行为描述面向快速建模与高速仿真，不承担生成硬件的职责。

本规划引入第二类描述能力——**可综合描述**：沿用同一套结构骨架（Module、端口、Wire、Reg、Mem、Assign、Update），通过限制数据类型与操作种类（§2），使模型的行为可以被机械地翻译为 Verilog（§3）。

两种描述的关系：

- 描述对象相同：同一个设计、**同一个模块类**——两个版本是类中的两个成员函数（§5）；
- 实现方式不同：行为描述追求表达力（任意 C++），可综合描述追求可翻译性（受限写法）；
- 正确性互相印证：两个版本在验证模式下并行仿真、observe 对拍（§4、§8）；完全可综合的子树再经 Verilator 对拍（§3、§8）。

| | 行为描述 | 可综合描述 |
|---|---|---|
| 状态 | 已实现 | 本规划新增 |
| 数据类型 | 任意 C++ 类型 | 受限（§2） |
| 操作种类 | 任意 C++ 操作 | 白名单（§2） |
| 用途 | 快速建模、golden reference | 生成 Verilog；也可原生解释仿真（较慢） |
| 内部实现 | 可以与可综合版不同 | 可以与行为版不同 |

## 2. 可综合描述的实现方式：两个限制 + 接口规则

可综合描述不引入新的结构概念，复用行为描述的全部结构骨架；可综合性由两个限制刻画：

1. **限制数据类型**：信号与状态的类型只允许具有确定位宽的硬件类型——Bool、定宽整数及它们的聚合（定长数组、Bundle）。动态容器、指针、堆分配等无硬件对应物的类型被排除。
2. **限制操作种类**：Assign / Update 的 lambda 体内只允许一个操作白名单——算术、位运算、比较、选择等可综合操作。任意宿主库调用（如 `std::sort`、I/O）被排除。

两个限制的含义：满足限制的模型，其每条动作的行为都是结构化、可静态翻译的——生成器不需要理解任意 C++，只需翻译白名单内的操作。

外加一条**接口规则**：凡要有可综合版本的模块，其 IN/OUT 端口类型必须可综合。接口在两个版本间天然一致——它们就是类的同一组成员端口（§5）——类型可综合则同一组端口值可以在行为树、可综合树、Verilated 模型之间机械传递，双模子模块"连接一遍就行"。代价：需要便捷好用的可综合复合类型原语（Bundle 等）来支撑复杂接口的表达，其细节另行讨论（§9）。纯行为模块（永不进入可综合树）的端口类型不受此限。

#### 类型系统（§9 第 4 条已定）

- **标量**：`UInt<N>` / `SInt<N>` 为基底类型（Bool 即 1 位无符号的语义特化）。它们承载两件事：位宽语义（两种描述的运算结果逐位一致的前提），以及生成期的操作记录。
- **原生整型兼容**：`bool`、`uint8_t`…`uint64_t`、`int8_t`…`int64_t` 允许声明端口与状态——存储兼容，值与 RTL 位向量一一对应；但**参与生成 RTL 的运算必须经 `UInt`/`SInt` 进行**：原生类型上的运算是 C++ 内建运算，生成器无法重载拦截，且其提升与符号规则同 RTL 有系统性偏差。实践形态：lambda 读入原生值后先转换、再运算。
- **复合类型**：分两类处理——
  - **Bundle 是框架感知的类型，不用 plain struct 加登记宏替代**。原因不在语法，在粒度：复合 Wire 的各字段常由不同逻辑驱动（字段级 SSA）；依赖追踪需要按字段精确（`valid` 变化不应唤醒只读 `payload` 的动作，脏驱动引擎的直接要求）；命名与波形需要 `top.w.field` 的叶子路径。plain struct 对框架是不透明整体，SSA、依赖图、别名、波形、端口展开都得为它各写一套特判展开；字段成为一等实体后，这些机制在叶子上原样运行，无需新规则。实现形态倾向**声明期展开**：`Wire<MyBundle>` 内部创建 N 个叶子 Wire、对外呈现 bundle 视图，框架核心只新增"可展开实体"一个概念，SSA 等检查照旧作用于叶子。字段声明语法（宏形态）待定（§9）。
  - **Vec 维持 `std::array<T, N>` 整体粒度**（框架文档 §3.3 的 ShiftReg 已在用）：元素级独立驱动的需求罕见，大数组本属 Mem 的领地；动态索引（`UInt<N>` 下标）生成 mux 树，常量下标免费，助手形式待定（§9）。元素级 SSA 日后确有需求再评估。

#### 操作白名单（§9 第 5 条已定）

白名单不是任意清单，而是 **`UInt`/`SInt` 类型库的 API 面**：库实现了的操作即白名单，未实现的操作在编译期就不存在——这是首选的违规检查方式（编译错误优于生成期报错）；少数运行期才能发现的违规（如动态循环界）在生成期报错并附层次路径。

**覆盖原则：与 SV 可综合子集对齐**。凡 SystemVerilog 可综合子集支持、且两态语义明确的操作都纳入白名单——`#delay` 等不可综合的 SV 行为本就不在覆盖范围内；综合代价是设计决策而非框架限制，代价高的操作（`/` `%`、大位宽 `*`）由生成报告（§6 的 manifest）标注提示，不一刀切排除。

**先定位宽语义**（操作清单的前提）：**定宽回绕**——每个值位宽固定；二元操作要求两侧位宽一致，不一致即静态错误，须显式 `zext` / `sext` / `resize`；结果位宽等于操作数位宽，溢出回绕。该语义与框架的显式哲学一致，且 C++ 实现（掩码）与 Verilog 翻译都直接。

| 类别 | 操作 | Verilog 映射 / 备注 |
|---|---|---|
| 算术 | `+ - * / %`、一元 `-`、`**` | 直接映射；`/` `%`、大位宽 `*` 在生成报告中标注综合代价；`**` 限常量指数 |
| 位运算 | `& \| ^ ~ ^~ << >>` | `>>` 对 `SInt` 为算术右移（`>>>`）；结果位宽取左操作数 |
| 比较 | `== != < <= > >=` | 结果为 Bool；禁止 `UInt`/`SInt` 混合比较，须显式转换 |
| 选择 | `mux(cond, a, b)` | SV `?:` 的唯一形态，见形态约束① |
| 位操作 | `x[i]`、`x(hi, lo)`、变基定宽片选、`cat(...)`、`rep(x, n)`、`zext/sext/resize` | `x[i]`、`x[hi:lo]`、`x[i +: n]`、`{...}`、`{n{x}}` |
| 归约 | `andR orR xorR nandR norR xnorR` | `&x`、`\|x`、`^x` 及取反形 |
| Bool 逻辑 | `! && \|\|` | 重载后无短路——白名单操作纯、无副作用，无实际影响 |
| Bundle | 字段访问、整捆拷贝 | 叶子级操作 |
| Vec | 常量下标、信号下标（mux 树） | 循环见形态约束② |

**三条形态约束**（比操作清单更重要）：

1. **数据相关的分支只有 `mux()`**：`if` / `?:` 无法被重载拦截，以记录值为条件的分支在生成期不可见；条件为静态常量（模板参数等）的 `if` 不受限——生成期正常选边；
2. **循环必须静态有界**：`for` 在生成期正常执行、自然展开，下标随之成为常量；
3. **普通函数调用自由**：lambda 内调用辅助函数在生成期自然内联，不受限——受限的只是叶子操作，组合结构不受限。

排除项只按**语义**划，不按代价划：四态语义（`x`/`z`、`===`/`!==`——wolvicmod 两态，与 Verilator 对齐）、浮点、动态容器与指针、宿主库调用。常量计算（`$clog2` 类）由 C++ `constexpr` 承担，不占白名单。被排除的需求走 DPI 行为岛（§6）。

## 3. Verilog 生成

生成的对象是**完全可综合子树**（§6）：子树内每个节点都有可综合版本。每个这样的子树经生成器输出一份 Verilog。结构概念到 Verilog 的映射是直接的：

| Wolvicmod | Verilog |
|---|---|
| In / Out | 模块端口 |
| Wire + Assign | wire + 连续赋值 |
| Reg + Update | reg + 时序块 |
| Mem + Update | 存储阵列 + 同步写口 |
| Update 优先级链（注册顺序） | 时序块内 if/else 顺序 |
| `.on(posedge(x))` / `.en(g)` | 敏感表 / 使能条件 |
| Module 层次 | Verilog 模块层次（或打平，待定 §9） |

观测点额外引出：observe 信号组的成员信号，在生成时原样追加为输出端口（§4.2）。

生成的 Verilog 不由 wolvicmod 自己仿真，而是交给外部仿真器（Verilator 等 cycle-based 仿真器）编译为 C++ 仿真模型，再链接回 wolvicmod（§7）。

生成纪律：生成从子树根的可综合版向下**按类展开**——每个节点的可综合实现是黑盒，其内部结构（含恰好复用他人模块类的子模块）是该节点的私有细节，不与行为树的节点建立"同一节点"对应；两棵树的节点对应关系由 §4.3 的配对规则给出，只锚定在建树时的 MOD 语句上。

## 4. observe

验证的核心问题：两套内部实现可能不同的描述，如何证明行为等价。回答是 **observe**——显式声明的观测点。

### 4.1 定义与声明形态

一个 observe 由三部分构成：

- 名字；
- 信号组：本侧实现内部的若干 WIRE / REG / MEM（或端口）；
- 摘要 lambda：读信号组、返回摘要值的函数；体内是任意 C++（与动作 lambda 同一哲学：结构显式、行为黑盒）。

双侧比对的不是原始信号，而是**摘要值**。摘要把"内部组织不可比"的两套实现映射到可比的值域上：例如队列的行为版内部是宿主容器、可综合版是指针加存储阵列，两者的 observe 各自读取自己的内部信号，只要摘要（如"有效项数 + 队头元素"）语义等价，对拍就成立。实现差异因此完全自由，契约只在摘要层面。

#### 注册写法（§9 第 1 条已定）

observe 在各侧实现函数体内注册（`behavioral()` / `synthesizable()`，§5），链式形态与 Assign / Update 一致：

```cpp
observe("occupancy").reads(cnt, head) = [](auto src) {
    auto [c, h] = src;
    return Occupancy{c, h};          // 摘要值
};
```

- `observe(name)`：给出局部名，创建时挂命名表并查重（与实体同款机制）；全局标识按 §4.3 拼出；
- `.reads(...)`：信号组，可含本模块的 Wire / Reg / Mem 与端口，以及直接子模块的 Out（与连线权限一致，框架文档 §2.2）；信号都是实现函数体内的局部实体（§5 规则 2），天然在作用域内。非实体的普通成员不可读——需要观测的中间值应显式声明为 Wire / Reg（框架文档 §3.1 的既有准则）；
- lambda：任意 C++，收 `std::tuple<const Ts&...>`（与动作同款），返回摘要值。摘要类型 D 须**可比对**（`operator==`）且**可打印**（失配报告用）；**可入波形**非必需——可波形化（`FstFormat`）的摘要随 FST 输出辅助失配定位，否则静默跳过（框架文档 §6.3 的类型规则同款）。配对两侧须返回同一类型 D（§4.3 的匹配检查覆盖）——实践上 D 在共享头中定义一次；
- 执行语义：observe 是纯观察者——只在拍边界（本拍 `eval()` 收敛后，与对拍拍协议对齐）求值，不写任何实体、不影响仿真语义；纯行为模式下 observe 不起作用（§8）；剥除（`-DWOLVICMOD_OBSERVE=0`，与 waveform_probe 的剥除开关同款）后模型行为不变。

**与 waveform_probe 的区别**：框架现有的 probe 更名为 **waveform_probe**——它是单侧的波形调试设施（字段引出、入 FST、逻辑不应读取）；observe 是双侧的验证契约（摘要、逐拍对拍）。两者声明形态相似（命名的只读提取），语义角色不同，保持两个 API。更名涉及框架文档 §6.3 与 `dbg/probe.h` 等实现，另行执行。

### 4.2 两侧的采样方式

- **原生树侧**（行为树、可综合树均为 wolvicmod 原生仿真）：`eval()` 收敛后（拍边界）执行全部 observe 的 lambda，直接读内部实体，产生本拍的摘要集合；
- **Verilated 侧**：摘要 lambda 不可综合，不参与 Verilog 生成；生成时把 observe 信号组的成员**原样**追加为输出端口。Verilated 模型的 `eval()` 结束后，适配层从这些端口读值，执行 observe 的 lambda 算出摘要。

两侧采样时刻对齐在每拍 `eval()` 收敛之后。

### 4.3 对应关系：树间配对、按名匹配

对比的单位是**两棵树中的配对节点**（§6）：两棵树从共同根向下平行构建，配对单位是"两侧由**同一 MOD 语句**创建的同名同类型子模块"，共同根本身天然是一对。共享构建逻辑（§5 规则 2 的红利）是配对的主要来源——两个版本都调用的辅助函数所创建的子模块，在两棵树中自动成对。

配对节点下，两侧各自声明的 observe 集合按**名字**匹配：名字相同的 observe 构成一对，要求摘要类型一致，逐拍比对摘要值。匹配检查在 elaborate 期完成——名字集合不一致（缺项、多项）或摘要类型不一致，都是建模错误，随结构检查一并报出。配对不上的节点（单侧独有的内部结构）不报错：它们的 observe 只记录、不对拍，作为调试资料。

用名字而非序号做对应键，与框架的命名哲学一致（框架文档 §6.1）：失配报告和波形里出现的都是可读的层次路径名。

每个 observe 另有**全局唯一标识**，取层次路径形式：`配对节点的行为树路径 + observe 局部名`（如 `top.core.queue.entries`）——行为树恒在，作为基准；可综合树侧配对后归入同一标识。唯一性由两级机制保证：模块层次路径全树唯一（框架文档 §6.1 的命名机制，创建时挂命名表并查重），observe 局部名在模块内唯一（创建时同样查重）。全局标识服务于失配报告、波形标注与观测记录的索引。

## 5. 模块组织：一个类、两个实现函数

同一个模块的两个版本组织为**同一个 Module 类中的两个成员函数**，而非两个类（完整示例见文首 §0）：

三条规则：

1. **接口一致且可综合**：两个版本共享同一份 IN/OUT 定义——它们就是类的成员端口，一致性是构造性的；类型必须可综合（§2 接口规则）。双模子模块在任一棵树中实例化都"连接一遍就行"。
2. **内部私有化**：WIRE / REG / MEM / MOD 不再作为成员变量——内部结构是单侧私有的，两个版本的内部本就不同。它们在各侧实现函数体内以**局部实体**创建：实体由框架持有，返回的引用只是句柄，创建宏在函数体内照常可用（`WIRE(T, w)` 展开为局部引用声明），命名表照常登记；observe 也在函数体内注册（§4.1），信号组天然在作用域内。只有 IN / OUT 是成员变量，因为接口是公共的。
3. **共存或二选一**：两个函数可以共存，也可以只写一个——
   - 只写 `behavioral()`：纯行为模块；可综合树中它也以行为侧出现（该子树不再完全可综合，不进 RTL，§6）；
   - 只写 `synthesizable()`：可综合模块，同时在行为树中**原生解释仿真**兜底——只是慢一点（结构更细、实体与动作更多，如排序网络对 `std::sort`）；
   - 两个都写：行为树取其快，可综合树取其真。

**共享构建逻辑**：两个函数同在一个类里，共享常量、模板参数、辅助函数与子模块工厂——相同的部分写一次，不同的部分各自表达。"层次写两次"的顾虑由此消解：重复被压进函数体内的差异部分；而且两侧共享的创建语句同时是 §4.3 配对关系的主要来源。

框架机制要点：建树期按当前树的性质调用各节点的对应函数（行为树调 `behavioral()`、可综合树调 `synthesizable()`，缺侧按规则 3 兜底）；普通构造函数保留给版本无关的设置。两棵树各自展平、各自 elaborate。具体编排待定（§9）。

## 6. 两棵树与完全可综合子树

- **MOD 不变**：`createChildModule` 照旧传一个模块类——双模性是类的内在属性（§5），MOD 不需要传两个参数；
- **建树**：行为树尽可能调 `behavioral()`，可综合树尽可能调 `synthesizable()`，缺侧按 §5 规则 3 兜底。两棵树形状允许在配对节点以下分叉（行为版与可综合版的内部结构本就自由）；
- **验证边界**：两棵树的共同根，其端口必须可综合类型（§2 接口规则）；边界以上是纯行为世界（testbench、激励器），根端口值逐拍机械拷贝给可综合树。纯行为探索可以把根直接架在任意类型的世界里；
- **完全可综合子树**：子树内每个节点都有可综合版本（DPI 行为岛除外，见下）→ 该子树可生成 RTL。验证模式下引擎自动识别（§8）。含行为侧节点的子树照常原生仿真，只是不进 RTL；
- **DPI 行为岛**：`synthesizable()` 内实例化的子模块若没有可综合版本（或内部越出白名单），生成器自动识别并桥接：Verilog 侧出壳模块与 DPI 导入调用，岛的全部状态由 C++ 侧持有、跨调用保持，第二遍编译时经 DPI 导出链接进来（§7）。识别为三分类：可综合则递归展开；不可综合但端口位宽确定则自动桥接；连端口都不可桥接则生成期报错附层次路径。**反静默**两条措施：生成报告（manifest）列出全部行为岛的位置与降级原因；严格模式（产出交付级 RTL 时）凡岛皆报错；
- **生成纪律**：生成树与行为树的节点对应只存在于配对点（§4.3）；放弃"沿行为树逐节点替换成可综合版"的生成方式——可综合版本的内部结构是其私有细节。

## 7. 构建流程：两遍编译

可综合子树生成的 Verilog 经外部仿真器编译为 C++ 后，再链接回 wolvicmod 才能仿真。完整流程：

```text
[第一遍编译]  wolvicmod + 模型源码（含可综合描述） ──> 生成器（可执行文件）
[生成]        运行生成器 ──> 识别完全可综合子树 + 每棵子树一份 Verilog（.v）+ 生成报告（行为岛清单，§6）
[外部编译]    Verilator：.v ──> C++ 仿真模型源码
[第二遍编译]  生成的 C++ + wolvicmod + 模型源码 + DPI 行为岛 + 对拍 harness ──> 仿真器（可执行文件）
```

要点：

- wolvicmod 参与两次编译，角色不同：第一遍是**生成器的宿主**（建模 API + Verilog 后端），第二遍是**仿真引擎**（两棵原生树 + 对拍调度）；
- 生成器识别完全可综合子树的逻辑与验证模式运行时所用的是同一份——构建期产物与运行时行为不会出现分歧；
- 第一遍的产物只有 Verilog 文本与生成报告，不含任何仿真状态；
- 第二遍把 Verilator 产物当作普通的 C++ 库链接，Verilated 模型经薄适配层接入对拍（§4.2）；DPI 行为岛也在这一遍经 DPI 导出链接进来；
- 两遍编译的工程编排（CMake 自定义命令 / 脚本）待定（§9）。

## 8. 仿真模式

### 纯行为模式

仅构建并仿真**行为树**（尽可能行为侧；只写了 `synthesizable()` 的节点以可综合版解释仿真兜底，§5 规则 3）。observe 不起作用，零验证开销。用途：微架构探索。

### 验证模式

从共同根开始形成**两棵树**——行为树尽可能选用行为侧，可综合树尽可能选用可综合侧——并行仿真，同一外部激励驱动两根：

1. **实现逻辑比对**：每拍 `eval()` 结束时，配对节点的 observe 按需对拍（§4.3）——验证行为版 ≡ 可综合版；
2. **生成后端比对**：引擎自动识别完全可综合子树，生成 RTL、经 Verilator 等 cycle-based 仿真器编译、并行仿真。RTL 版本**仅接受输入激励**（不回驱任何树）；每拍 `eval()` 结束时，其输出与 observe 结果与**可综合树**比对——注意不是行为树：这一段验证的是"wolvicmod→Verilog→Verilator"的翻译忠实性（可综合版 ≡ RTL），保持纯粹，不掺入实现逻辑差异。

两条比对各管一段，失配定责清晰：逻辑问题在第一段暴露，后端问题在第二段暴露；行为版 ≡ RTL 由两段传递得出。

可预见的扩展：纯 RTL 模式（整棵树替换为可综合实现，测 RTL 级性能、作为流片前的验证形态）——是否纳入本规划，待定（§9）。

## 9. 待定细节

以下决策点留待讨论细化：

1. ~~observe 的注册 API~~（已定，见 §4.1）：残留：摘要类型的共享头组织方式；waveform_probe 更名的执行（框架文档 §6.3、`dbg/probe.h` 等）；
2. observe 名单的归属：纳入共享接口定义（由接口强制双侧覆盖），还是各侧实现各自声明、按名匹配（当前 §4.3 按后者写）；
3. ~~驱动适配~~（已取消）：两侧由同一组端口与普通连线驱动，Verilated 侧由框架按端口布局表机械拷贝，无需专门设施；
4. ~~可综合类型系统的选型~~（已定，见 §2）：残留：字面量语法、混合符号运算细则、Bundle 字段声明语法、动态索引助手的形态；**可综合复合类型原语的易用性**（接口规则的代价，§2）；
5. ~~操作白名单的具体范围~~（已定，见 §2）：残留：代价标注在生成报告中的形式、`**` 非常数指数的处理、流式操作（`{<<{}}` / `{>>{}}`）是否纳入、移位量位宽规则；
6. `behavioral()` / `synthesizable()` 的建树调用机制：树的性质如何传入、两棵树的构建与 elaborate 编排；配对规则的具体化（"同一 MOD 语句"判据的实现）；
7. 两遍编译的构建编排：CMake 自定义命令的组织方式、增量重建策略；
8. 语义边界：组合环、多时钟、Mem 同步读、初始值在两种描述间的差异、DPI 行为岛的求值语义（输入采样与输出驱动时刻、组合直通）；
9. 生成 Verilog 的层次策略：保留层次还是打平；
10. Verilated 侧观测的引出范围：仅完全可综合子树的根，还是递归引出内层（追加端口 / Verilator 公共信号）；
11. 纯 RTL 模式是否纳入本规划。
